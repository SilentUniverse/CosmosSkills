# 以任务交付为中心的智能体开发工作流

本文提出 CosmosSkills 的工作流演进方案：让明确的需求能够直接完成，让跨会话的工作能够可靠接续，让开发中获得的有效知识持续改善后续任务。文中描述的是拟议机制；具体执行仍以仓库生效的规则和用户授权为准。

工作流的首要目标是完成用户要求的结果，并提供与风险相称的验证证据。Spec、issue、handoff 和代码地图分别解决需求决策、执行协调、会话恢复与知识检索的问题。它们是否需要出现，应由任务中的实际需要决定。

每个任务都需要一个最小执行约定：要达到什么结果，必须保留哪些约束，如何判断完成，以及哪些动作已经获得授权。这些信息可以来自用户请求、有效文档和当前对话，不必为每个需求创建文件。缺少实现细节时，执行者应调查代码和环境，自行选择符合既有约定的方案；只有仍未解决的选择会实质改变结果、范围、公共接口、不可逆影响、成本或权限时，才需要用户作决定。

模型能力提升，可以使一次连续执行容纳更多明确的工作。流程应允许这种变化，同时保持完成标准和证据要求。不能仅凭模型自信，认定需求已经明确、代码没有冲突或任务已经完成。

**能否自主执行、是否需要持久记录、需要加载哪些上下文，是三个独立判断。** 一个需求已经明确，但需要排队或分派，适合写 issue；一个需求需要用户确定产品语义，即使只改两行代码，也需要先解决那个决定；一个任务由同一执行者连续推进，只是跨越了会话边界，可以用 handoff 接续，无需仅为恢复而补建完整 issue。

因此，有界改动应当指目标、约束和完成标准明确的工作。文件数量、模块数量和实现步骤数量不能单独决定是否进入 Spec。涉及更多模块会扩大需要调查和验证的范围，却未必产生新的产品决策。

直接执行的适用条件是：有效需求与授权足以支持下一步，已有合适的验证路线，相关协作状态能够保持一致，执行者能够在真实边界到来前保存未完成工作。用户要求先审方案时，审阅检查点继续有效。切换技能或省略 issue 都不能绕过它。

“新需求与现有状态不冲突”需要通过相关范围内的检查建立。入口可以是功能名称、代码路径、接口符号和现有任务指针。先检查相关代码、有效约定和任务状态摘要，只有发现依赖或歧义时才扩大阅读范围。查不到同名 issue，不能证明功能不存在或与其他工作无关；也无需为一个局部需求逐张重读全部历史 issue。

这里的状态包括三方面。产品状态涉及既有行为、验收条件和长期决策；协作状态涉及任务归属、分派、依赖、写入范围与共享运行资源；验证状态涉及证据所对应的代码和环境。新需求可能保持原有行为，却提前完成一张待办卡、改变另一项工作的依赖，或使已经运行的检查失效。这些影响都需要对账。

例如，给一个没有关联待办的导出功能增加明确的排序选项，可以直接实现、验证，并更新必要的使用文档。如果某张 ready issue 已经要求增加该选项，则应核对其完整验收条件，沿原任务记录证据和完成状态，避免后续重复实施。如果用户明确要求替换已经交付的导出格式，执行者应保存合同替代关系，并检查相关调用方。替换意图已经明确时，只有尚未解决的实质性后果需要再次询问。

有活动分派的工作需要先协调。主执行者不能在其他执行者仍依据旧任务输入运行时，悄悄改变其范围、写集或共享资源。没有新 issue 的任务也不能成为批次中无法解释归属的改动。明确归属、更新受影响输入、完成必要的重新验证之后，才继续推进。

**issue 应当完整表达被追踪的工作，但可以只覆盖项目工作的一部分。** 它适用于需要排队、分派、依赖管理、合同替代记录或特定追溯要求的场景。没有这些消费者的需求，可以在当前任务中执行到完成。过程中出现持久记录的需要时，再使用对应载体。

这也限定了状态工具的承诺。由 done issue 派生的视图，只能表达已追踪工作的交付记录。实际行为需要结合代码和运行结果判断，预期行为需要结合有效约定判断。issue 队列为空不能代替用户目标验收。即使每个切片分别通过测试，仍需检查最终集成结果，以及用户要求中没有被切片覆盖的部分。

Spec 负责解决需求与执行方案中的实质性问题，并在确有持久消费者时形成相应文档。TDD 负责通过行为测试推动实现和验证。文案、配置和机械修改采用能够检测相关失败的现有检查，不为满足流程外观编写无价值的新测试。任何执行路径都保留仓库要求的门禁、必要的集成验证，以及尚未完成的人工或外部验证事项。

工作能够连续推进，还依赖已经建立的代码理解。执行者可能已经弄清楚调用链、状态所有者、隐含约束和关键测试。切换步骤或 issue 时，只要这些理解仍然适用，就应继续使用。下一步需要读取的材料，由当前动作与缺失信息决定。有效验收约定已经包含在上下文或执行包中时，无需全文重读原 issue；某项关键约定只存在于历史记录中时，仍需读取对应部分。

“读过哪些文件”只能提供粗略入口。更有用的上下文是文件或符号与下一步的关系，以及由阅读得到的关键判断。例如，上传任务准备增加重试时，知道请求封装已经重试、调度层负责更新状态，会直接改变实现位置和验证重点。交接时应保留这个关系，并指向能够核实它的代码，而不必复制整个源码或调查过程。

**有限上下文要求工作流同时维护可恢复的执行状态和可复用的项目知识。** 执行状态随任务推进不断替换，项目知识需要经过筛选、验证和更新。两者使用不同的生命周期，才能避免临时假设进入长期规则，也避免任务结束时丢掉有价值的理解。

| 信息 | 保存位置与用途 | 生命周期 |
|---|---|---|
| 未完成目标、下一步、当前证据、任务内假设 | 当前上下文；跨会话时写入 handoff | 剩余任务完成或明确取消后清理 |
| 排队、分派、依赖、验收及完成记录 | issue 与其现有调度机制 | 按任务历史和合同规则维护 |
| 可重复触发的错误或行为约束 | 测试、类型约束或现有检查 | 随有效行为约定维护 |
| 难以从代码直接恢复的模块关系与隐含约束 | 对应模块的代码地图或知识块 | 相关代码、环境或约定变化时核实并更新 |
| 领域含义、符合条件的重要取舍 | 词汇表或 ADR | 按术语和决策的治理规则维护 |

长期留存需要回答两个问题：这条知识会怎样改变后续任务的判断；后续执行者从哪里找到它。普通文件位置、导出列表和容易搜索恢复的关系，通常按需查询即可。困难的语义约束、已确认的失败机制和不显然的设计取舍，才值得承担持久记录的成本。没有合格发现的一轮开发，可以不增加任何知识条目。

能够自动检测的错误，优先交给测试或现有检查。测试的预期来自需求、有效约定或独立示例，不能照抄实现逻辑来证明自身正确。文档保存测试无法充分表达的约束、适用条件和原因；同一事实已有权威位置时，更新该位置，其他载体用引用连接。

代码地图的常驻入口保持简短，具体知识靠模块和任务指针逐步展开。记录关键知识时，保留足以核实它的代码、测试或决策依据，必要时注明适用的环境和版本。读取知识时，只加载相关部分；发生相关变更时，同步修正、删除或替代。某次环境故障导致的失败尝试，不能被写成无条件、永久有效的禁止规则。

知识应在得到充分证据后及时写入合适的位置，至少在会话边界和任务清理前完成必要转存。不必等整个需求结束才保存，也不必每个工具调用后都写摘要。稳定知识即使来自已经完成的步骤，也可以继续服务未完成任务和未来开发。

上下文边界应由实际可用空间和恢复需要决定。连续工作仍然合适时，继续执行；接近不可避免的边界时，留出写入、检查交接信息的空间。自然切片完成是方便的交接点，但无需为了等到全绿而丢失现场。测试失败、实现只完成一部分或验证仍在运行，都可以如实交接。

一份可用的 handoff 应当让没有会话历史的执行者恢复以下判断：

| 要恢复的判断 | 需要保留的信息 |
|---|---|
| 还欠用户什么 | 未完成目标、验收条件、有效授权、约束与未决选择 |
| 工作现场在哪里 | 仓库、分支和基线，相关改动归属，活动分派或外部任务入口 |
| 哪些理解会影响下一步 | 最小代码入口、关键关系、已确认约束，以及明确标记的假设 |
| 验证到了哪里 | 实际通过或失败的检查、对应代码和环境、证据路径、剩余验证 |
| 怎样继续 | 具体读取范围、命令或编辑动作、预期可观察结果，以及已知障碍 |

交接复用现有的 Continue、State、Decisions 和 Avoid 等位置，有权威来源的内容保留指针。只存在于对话、又会影响后续决策的信息，才需要在交接中写明。完整日志、完整 diff、普通探索历史和可轻易重建的文件清单不进入常驻上下文。命令、路径和关键标识必须准确，仍在运行的任务要有查询入口，避免恢复后重复启动。

恢复工作时，先确定剩余目标和下一步，再检查相关代码、工作区、环境及授权是否变化。没有变化且仍适用的理解可以复用；控制当前改动的关键事实要从有效来源核实。受到变化影响的验证需要重跑，其他已经通过且适用范围未变化的检查可以继续使用。交接记录提供恢复路径，不能单独证明代码正确。

完成任务需要回到完整用户目标，核对结果、必要检查和仍未完成的事项。局部测试通过、issue 标记 done、第一条续接命令执行成功，都只能证明各自覆盖的范围。清理 handoff 之前，应确保仍有长期价值的约束已经存入对应位置。任务历史可以保留，临时探索与已消费的恢复信息按生命周期清理。

这套方案在 CosmosSkills 中需要同时调整入口规则和下游消费者。共享执行规则由 [CLAUDE.md](../claude/CLAUDE.md) 承载；[Spec](../workflow/spec/SKILL.md) 与 [TDD](../workflow/tdd/SKILL.md) 负责对应阶段的具体行为；[handoff](../workflow/handoff/SKILL.md)、[resume](../workflow/resume/SKILL.md) 和 [map](../workflow/map/SKILL.md) 分别维护续接与知识规则。实施可以按以下顺序形成可验证的改动：

1. 分开自主执行、持久记录和用户审阅的触发条件。允许明确任务直接推进，保持有效授权与用户要求的审阅边界，并让所有实现入口都能检查相关状态。
2. 调整状态投影和批次审计的范围。状态投影明确只覆盖已追踪工作；批次基线区分历史测试与本批贡献，对新增、修改测试及其他本批改动核对归属，保留必要验证，禁止为通过门禁虚构 issue 归属。
3. 使知识留存独立于 issue。没有 issue 完成块时，已确认的长期约束仍有可检索位置；缺少代码地图时，按实际知识需要建立最小入口，避免为了留存一条事实先做全库整理。
4. 完善交接和恢复。无 issue 任务跨会话时能够保留完整的剩余目标和证据；恢复能发现相关漂移，复用适用的知识与验证，并在完成后正确清理临时状态。

验收应覆盖具体反例：无 issue 需求可以实现并通过必要检查；提前满足已有待办时不会重复实施；活动分派不会被未协调的改动覆盖；历史无 issue 测试不会阻塞未来批次；没有 issue 的任务中断后仍能接续；知识依据变化时不会继续无条件套用旧结论；队列为空但用户目标未完成时不会报告全部完成。

确定性检查可以验证规则引用、记录格式、归属边界和恢复机制。实际交付是否更快、更可靠，需要在用户明确授权的行为评估中观察完成质量、重复探索、已知错误复发和交接遗漏，不能从文档长度或检查通过数量推断。方案期望积累的是后续任务能找到、能核实、能据此行动的有效知识，同时让每次执行承担与实际需要相称的流程成本。
