# 工作流实现、验证边界与效果测评

Schema 3 的增量协作包含计划修订、输入绑定、独立实施与人工审查、反馈回流、可携带证明和
实际临时文件清理。Schema 2 保留可执行的顺序批次，schema 1 只提供准入兼容。
日常操作见[使用说明](checkpoint-local-release.zh.md)，关系与边界见
[协作设计](incremental-collaboration-plan.zh.md)。

## 目标的证据口径

| 目标 | 可检验机制 | 收益结论所需的额外证据 |
|---|---|---|
| 更高产物质量 | 实际候选/契约/产物验证，拒绝过期接受、漏掉义务和空绿 | 对相同真实任务的隐藏验收和缺陷率比较 |
| 更快完成 | 成熟场景优先交付，审 A 时做独立 B，共享活动检查、显式环境契约下复用，局部清理自动执行 | 含失败、返工和人工等待的端到端配对耗时 |
| 更少 token | 短入口、按需协议、工具摘要、机械推进不调用模型、无通知监督模型 | 全部 Agent 的 provider 实际 usage，包含缓存与失败调用 |
| 固定版本可审 | 实测 release、完整入口、版本化人工结论，源码预览持续可用 | 在目标 OS/CPU 和真实用户环境运行相应交付 |
| 非 UI 无 UI 成本 | 禁读/禁导入/进程审计覆盖普通入口和 schema-3 闭环 | 这个精确零值只指 UI 专属成本，不指所有 Python/IO 耗时 |

不能用“结构检查通过”宣称端到端更快或模型生成吞吐没有回退。实际模型 usage、TTFT 和
生成区间尚未测量时记为 null。当前数值及源文件身份见
[增量成本](benchmarks/incremental-cost.md)和[验证记录](benchmarks/incremental-validation.json)。
这些记录只覆盖其源文件哈希对应的版本；测试治理的使用和新验证记录见
[测试质量与成本治理](test-governance.zh.md)。

## 对抗审查约束

以下反例由实现和回归共同约束，覆盖版本证据、实际输入消费、关闭义务及清理边界。

| 反例 | 必须成立的边界 |
|---|---|
| 工人按决定 A 开工，完成时被改记为消费了 B | 派工就绑定输入；过期结果需协调后再交回 |
| 检查因输入变更被拒收，此后同源码永远无法取得证明 | 输入过期与实际行为失败分开；真实失败保留约束 |
| 人审包 A，final 在同源码下生成不同包 B | 实际 artifact、入口、环境和场景检查决定能否沿用 |
| final 换包后只检查能启动，却把原场景标 green | 缺少完整 `final_checks` 对应及真实通过结果时不创建可审版本 |
| 等人时 Issue 或人工标准被改写，仍直接关闭 | 发布完成前重新核对当前工程契约与外部依赖 |
| 审查约定修订后收到旧批准 | 旧版本不接受；无关工作不使有效 A 误失效 |
| 下游只通过人工决定依赖上游，被失效传播漏掉 | 工程和决定边使用同一传递关系；环在准入前拒绝 |
| 人工检查没有分配或需求缺机器证据 | 保留待办并拒绝关闭，不能靠空队列消失 |
| 删除已发生、状态事务中断 | unlink 意图预先持久化；重入核对实际文件且不重复计删除 |
| GC 预览后文件被改、引用增加或进程仍活跃 | apply 重新核对，只删除归属和终态明确的文件 |

测试验证实际运行、跨平台锁/进程、安装器、打包、UI 路由和证据校验；技能结构检查验证
入口、链接和常驻预算。规则文字的逐字相等不作为行为通过证据。

## 验证与局限

执行命令和结果身份以[验证 JSON](benchmarks/incremental-validation.json)为准。
新场景在 `tests/test_incremental_workflow.py`，兼容和运行基础在 managed、batch、resources、
checkpoint_store、supervisor、workflow_state 与 UI routing 测试中。

macOS 真实夹具覆盖 PyInstaller onefile/onedir、Node 官方 SEA + esbuild 的构建、验证、导出、
解包、移除开发源模块后直接运行；Chromium 夹具先暴露旧响应覆盖新选择的缺陷，再修复并完成
同一批次。无 UI 入口不会运行这些显式 UI 夹具。

CI 配置 Linux/macOS/Windows 基础检查、真实浏览器和三种打包矩阵，npm/pip 缓存只在需要的
作业使用。本机不代报 Linux/Windows CI 已执行，也没有真实硬件、商业签名、所有打包器或
任意 CPU 架构的兼容认证。

[需求覆盖清单](checkpoint-coverage.json)保留具体场景文义和证据位置；代表性覆盖、实际运行
和平台待验分开。设计里的 V01–V36 也是目标场景列表，不能直接当成 36 个全平台通过数。
历史固定版本和依赖证据持续保留；GC 没有自动删除交付包的保留期策略。

## 开发者测评方案

1. **基础正确性。** 执行 `python3 -m unittest discover -s tests` 和
   `python3 scripts/validate-skills.py`。核对失败与平台跳过，跳过不得计作通过。
2. **固定版本协作。** 在一个真实项目提出“导入可审时给 A，期间继续搜索 B”。确认 A 已实测
   才提醒、B 持续推进、决定消费者等待。改动主仓库后重开 A；实际包身份和行为应仍对应 A。
3. **反馈和需求变更。** 对 A 提交取消操作缺陷；观察定向修复和 B 的重审。再提出覆盖同名文件
   的新要求，确认建关联增量且保留原历史、预算不重置。旧批准不能通过新的场景。
4. **清理和复用。** 产生探测脚本、临时图片、回归测试及反馈材料。执行 `/tidy inspect feature`
   后再 `/tidy feature`，核对真实删除字节、变化文件保留、未解决反馈保护、测试及 A/B 仍存在。
   在另一个目录保留 Issue 与 `receipts/managed` 后核验历史，并复用取消场景测试。
5. **通知。** 分别记录前置满足、封存、交付、宿主确认、人工决定的时间。测试主控忙碌、宿主
   短暂离线、发送后确认前中断和版本撤回。默认 parent-turn 与真实 host 适配器分开报告。
6. **真实包/UI。** 按项目目标 OS 运行 `scripts/check-native-packaging.py` 的三个 `--kind`；
   显式 UI 项目执行 `scripts/check-ui-fixture.py --setup --output NEW_DIRECTORY`。
   安装只发生于这些明确选择的夹具，不进入普通非 UI 流程。
7. **CLI 配对。** 保留修改前实际文件目录，用 `scripts/benchmark-checkpoint.py
   --baseline-directory BASELINE --samples 31 --output RESULT.json`；可加本地 tokenizer encoding。
   每组 3 次预热，交错先后次序，在没有其他测试/构建的同一机器上运行，比较 p50/p95、配对
   区间与输出语义。不用 CLI token 数除以 Python 时间伪造模型 token/s。
8. **完整任务 A/B。** 显式启用模型评估后，先跑非 UI 修复、异步人审、反馈后清理三类各两次，
   新旧共 12 次，再扩为八类各三次共 48 次。固定起点、需求、隐藏验收、模型和推理设置，随机
   交错顺序，区分冷热依赖缓存，隔离工作树/端口；由不知道版本的评审判断产物质量。

每次记录用户技能切换、重复确认、手填 ID、人工审核次数、完整检查次数、构建/压缩耗时、
AI 空闲和返工。provider input/cached/output/reasoning usage 计入所有 Agent、失败与修复。
人工等待、TTFT、生成时长单列，缺字段留 null。新协议特有场景使用相同目标的人工协调工作流
作基线，不能拿“不履行义务”的对照组比较速度。

先保证隐藏验收、版本完整性和零误删，再比较同等质量下的完整时间与 token。任何稳定回退
都要解释其消费者和保护价值并消除可避免开销；没有测量的收益保持未证实。
