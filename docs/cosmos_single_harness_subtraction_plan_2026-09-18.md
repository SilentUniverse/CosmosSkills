# CosmosSkills：单 Harness 协作减法方案

日期：2026-09-18  
源码核对基线：`SilentUniverse/CosmosSkills@1d70fd79c43b2ac5accb526f54631de747b68190`  
用途：在获得实施授权后，供 AI 按现有 Spec → TDD 工作流执行。本文是方案，不是已完成的代码改动或真实宿主验收报告。

## 1. 目标和结论

用户只在一个已选定的 Codex 或 ZCode 中工作：说明需求、看 Spec、执行 TDD -p、中途直接反馈、查看进度、最后接收汇总。UI 工作优先使用当前宿主真实可用的视觉与浏览器能力。

Cosmos 保留目标、契约、任务归属、验证证据和必要恢复；会话、子 Agent、工具权限、消息传递与运行生命周期优先交给原生 Harness。不要增加第二套 Agent 调度服务。

本轮应以减法为主：取消无当前消费者的架构提案，退出重复的默认动作，修正错误的生命周期和进度表达，验证一条真实的人机协作路径。减少概念和使用步骤，不以减少代码行数或测试数量为目标。

### 已经完成的工作，不重复建设

基线已包含 PR #123 的 managed runner 有界诊断分支，以及持久化的 diagnose/repair 控制与相关测试。`tests/test_overnight.py` 中使用脚本化会话、真实 schema-3 批次和检查，验证失败后修复并关闭；这不是实际大模型能力证明。[R1][R2]

`UI-TESTING.md` 已规定优先复用宿主 browser-use，缺少必要能力时才补项目级 runner。不要重新写一个表达同义原则的 UI 平台。[R4]

## 2. 九定律如何约束取舍

| 定律 | 本轮决策 | 不能误用成什么 |
|---|---|---|
| First Principles | 优化用户完成目标、反馈和验收的路径 | 看外部项目有 Coordinator 就再建一个 |
| Invariant | 保留所有权、有效证据、授权、版本和资源边界 | 为了方便，直接把聊天结论写成机器通过 |
| Parsimony | 删除重复概念、状态和固定仪式 | 以代码行数、注释长度或文件数量衡量简洁 |
| Locality | 先改并行交互规则、状态展示和 UI 使用路径 | 重写整个运行时或同时适配多个宿主 |
| Provability | 运行事实来自宿主；验收结论来自有效证据 | 两套会话状态机、两套任务表相互同步 |
| Adversarial Review | 用中断、旧结果、反馈未送达和工具缺失攻击方案 | 为每张小卡强制增加多个审查 Agent |
| Empiricism | 测量实际任务的完成、重复工作和人工介入 | 未测量就宣称省 Token 或扩大并行一定提速 |
| Reversibility | 先退出默认路径，再按真实消费者决定代码退役 | 直接删除旧批次运行时、证明和历史 |
| Evolution | 一次做成一条用户路径，再逐步扩展 | 先建设通用协议、平台和多宿主矩阵 |

仓库的 Parsimony 定义本身强调最少的概念、状态和特例，而不是最少 LOC；九定律在相关设计点使用，不应再变成每张卡都提交九段报告的仪式。[R3]

## 3. 取消、降级、删改与保留清单

### 3.1 取消此前提案，不启动建设

这些是从前面方案撤下，不代表当前仓库已经有对应模块需要删除。

| 提案 | 处置 | 当前替代 |
|---|---|---|
| 独立 Coordinator 大模型、强制主 Agent 不编码 | 取消强制角色分层 | 当前主会话负责目标，也可承担自己拥有的一项实现 |
| 新 Cosmos Session Protocol / AHP 接入 / 多客户端同步 | 本轮不做 | 使用所选宿主的线程、续接和原生消息 |
| 重写为 snapshot + 全局 ordered-event reducer | 本轮不做 | 保留既有状态、revision、事务、回执和恢复机制 |
| Claude/OMP/Codex/Pi 通用适配器矩阵 | 本轮不做 | 验证当前实际宿主；只有第二个真实消费者需要时再提取公共接口 |
| 通用 Context Resolver、记忆数据库、全仓知识图谱 | 本轮不做 | 已有 packet、briefs、最新失败引用、CODEBASE/ADR |
| 通用视觉模型路由与固定“观察—编码—验收”多 Agent 组合 | 取消默认流程 | 具备所需能力的单个执行者先实现并自验，必要时独立审查 |
| 独立实时看板、Mellos 双向控制、自动修复图编辑器 | 本轮不做 | 原生执行面板加 Cosmos 只读投影 |
| 全局遥测平台、模型成本调度器 | 本轮不做 | 复用已有回执和显式评测，缺失的实际 usage 保持未知 |

### 3.2 保留能力，但从日常默认路径移走

**overnight。** 保留刚增加的有界诊断及回归，作为明确选择的外部无人值守运行方式。正常 Codex/ZCode 主会话不自动启动它，不再嵌套启动另一个 Claude CLI。不能同时让原生 Goal、外部 runner 和 Stop-hook 各自控制重试。

**schema-3 managed batch。** 不要求用户记住版本或 batch ID。仅在确实存在固定版本接受、版本化决定、资源生命周期、持续协调或持久证明等消费者时使用。一般小任务保持 inline 或普通任务队列。已经建立的活动批次继续按原协议运行，不能静默降级。

**正式审核、打包、视觉评分。** “跑起来让我看看”默认是开发预览；“锁定 A 给我正式验收”才走相应固定产物流程。功能性 UI 验证不默认增加 graded 评分。适用项目已有的构建、回归和交付门不因简化而消失。

**交接文档、完整协议加载。** 连续会话复用已核实上下文；真实会话或上下文边界才做 handoff。已存在的 packet/brief 不再改写成一份“更完整摘要”。

**测试与 PR 重复工作。** 提交阶段消费上游证据，不为凑 Evidence 再运行一遍。代码、依赖、契约或集成结果变化导致旧证明不再适用时，必要重验仍然保留。最新 `/pr` 已声明不自行再跑套件、不默认等待 CI；不得把“已合并”和“CI 已通过”混为一谈。[R8]

### 3.3 当前仓库里实际需要删改的两处

**第一处：统一的回合生命周期假设。** `DRAIN-PARALLEL.md` 当前把开放波期间不能结束回合、会话退出杀死所有 worker 写成统一规则。ZCode 文档明确后台子 Agent 可以跨当前回合继续，因此应删除该跨宿主绝对化结论，改成依据当前宿主实际能力处理。[R5][H1]

要保留：未确认 worker 终态不能收波；开放共享树波不能补派新波；未收口不能宣称已交付；宿主能力不明时不能假装存在后台续跑。

**第二处：把所有未收口执行叫作 zombie。** 当前 `feature_frontier()` 只依据 dispatched 与 closed 的差集生成 `zombies`，`render_survey()` 直接显示 zombie；这无法区分活跃任务、结果已返回但未归集、真正失联。[R6]

先改面向人的标签为“执行未收口；运行状态以宿主为准”，不直接改 legacy JSON 键或调度退出码。不要从没有心跳推断死亡，也不要从有 execution ID 推断进程正在运行。

### 3.4 可选降级：注释长度硬门

`comment-gate.py` 使用 3 行/240 字符门槛，并有 banner 和 workaround 豁免；源码也承认它只是机械代理指标，不能证明注释有用。[R7]

建议将“仅因长度超限阻断完成”降为审查提示，或者只在用户明确选择的项目保留硬规范。保留对解释不变量、并发、协议、生命周期的必要说明，不增加更多豁免标记解决例外膨胀。

该项改变了已接受的风格约束，应单独确认、单独提交，不与不改变验收强度的协作修复混在一起。确认前维持当前门与测试。它不等于删除安全说明、许可证要求或其他实质检查。

### 3.5 绝不能以减法为名删除

保留任务写入归属、共享资源互斥、共享工作树整波归集、候选/产物/证据绑定、首次失败、原目标累计约束、真实授权、当前目标关闭检查，以及已有回归与历史证明。

原生 Agent 的 completed 只说明宿主执行结束，不自动证明产品通过。Goal Mode 的完成判断不替代 Cosmos 已承诺的最终验收义务。

## 4. 剩余落地工作：两个改动 PR，加一次 UI 实际验收

### PR-A：原生会话中的执行、等待和聊天纠偏

**目标：** 用户仍然只使用 Spec → TDD -p → 直接反馈；不操作另一套编排器。

**首选修改位置：**
`workflow/tdd/DRAIN-PARALLEL.md`、`workflow/tdd/DRAIN.md`、`workflow/tdd/SKILL.md`。
仅在需要恢复入口或公开使用说明时同步相关文档，避免相同正文复制到多个 Skill。

**实施内容：**

1. 删除跨宿主“一旦回合结束，所有 worker 都终止”的假设。使用原生完成/注意事件；确实没有事件时，保留有界的原生状态读取或等待。不要把 30 秒/1 分钟监督节奏变成所有宿主必需的模型心跳。
2. 明确三个不同事实：主回合结束、子 Agent 终态、工程波已归集。只有宿主实际确认终态、现有归集检查通过，才能推进对应工程状态。
3. 具备可靠后台与结果接收路径时，允许给用户“仍在处理”的回合回复；未知或不具备时使用前台等待或先安全停止。结束回合不释放文件/资源归属。
4. 用户纠偏先定位受影响的 assignment。约定内修复转交原生 worker；更改任务契约时先等相关写入者安全返回，再走已有 Spec/修订路径。不静默改写 worker 已绑定的输入。
5. 原生消息已送出，不等于指令被消费或旧动作已停止。证据不足就如实报告；不能同时由主 Agent 改 worker 的文件。无原生消息能力时，在安全边界回收后继续，而不是创建外部消息服务。
6. 并行只用于独立工作，保留当前并发上限和整波屏障。不要因为原生宿主能动态开更多 worker 就修改共享树调度模型。

**验证：** 优先复用现有失败/恢复和增量协作测试。规则行为在真实宿主或显式行为评测中验证，文本包含某句话不算行为通过。需要有“支持原生后台”和“不支持/未知后台”两条路径；支持路径能中途回报进度，未知路径不误报可后台运行。

**不做：** 新通用 adapter、后台守护服务、额外 Coordinator、原生 Goal 与 overnight 叠加控制。

### PR-B：让现有工程投影可读，不创建第二份任务表

**目标：** 用户问“做到哪了”就得到可靠摘要，无需再让模型翻完整历史推理。

**首选修改位置：**
`workflow/workflow-state.py` 的 `feature_frontier()`、`incremental_view()`、`render_survey()`、`render_human()`；
`workflow/tidy/SKILL.md`；
`tests/test_workflow_state.py` 与确有交集的 `tests/test_incremental_workflow.py`。

**实施内容：**

1. human 输出把未经宿主证实的 zombie 改为“执行未收口”，保留现有 JSON 字段和消费者兼容。
2. 存在 managed batch 时，读取既有投影的 action/reason_code、review、feedback 和可用证据引用。不能仅凭 issue status=ready 推断已允许派发，决定依赖仍由现有调度器判断。
3. 输出按“目标范围、已记录完成、未收口执行、受阻原因、待人决定、下一步、证据入口”组织。只显示来源能够支持的信息。既有 done 记录没有当前适用证明时，不标成“当前已验证”。
4. unknown 是合法结果。没有宿主事件接入时明确说明仅展示持久工程状态，不扫描陌生 PID，不启动后台监控。
5. 默认直接 stdout/原生面板，不增加 SUMMARY 真值文件。确实需要侧边固定预览时，才将同一输出导出为只读缓存；缓存应带生成时间和来源身份，不参与调度或完成判定。
6. 查看状态不运行测试、不启动模型或浏览器、不清理文件。更新发生在有意义的边界，非固定周期生成模型报告。

**验证：**
正常未收口不会被标成死进程；待审 A 不掩盖独立 B；明确暂停/决定缺失的原因可见；卡片全 done 但 final 未通过时不显示目标完成；读取前后无状态写入；原 JSON/CLI 消费者继续工作；来源损坏显示缺失证据而非空绿。

**回滚：** 单独撤回渲染及说明改动即可，不迁移持久状态。

### 验收 C：在选定的一个 Harness 里完成 UI 反馈闭环

这不是新平台 PR。先使用现有 UI 规则和现有夹具做一次真实使用验收，只修暴露出的缺口。

**选择：** 先跑用户当前主要使用的一个 Windows Harness；另一个作为后续兼容验证，不同时建设多宿主框架。

**能力确认：** 在任务确实涉及 UI 时，确认被选执行者拥有实际浏览器操作、所需观察与图像理解能力。视觉模型名称不是工具可用性的证明；使用最小必要权限，不把全部工具或全部凭据泛化授权。

**执行者：** 主 Agent 本身具备能力就直接做；需要专门模型时使用一个原生 UI worker；子 Agent 缺浏览器而主会话可用时，改由主会话操作验证，不另起 Harness。高风险场景的独立审查义务不因单 worker 自验而被取消。

**场景：** 一个独立的非 UI 卡与一个 UI 任务并行；用户中途指出取消/异步显示错误；主会话协调相关 worker；使用可控制的事件顺序复现，修后重跑原场景，记录必要证据和最终汇总。共享页面或设备保持单操作者。

`tests/ui_fixture` 与 `scripts/check-ui-fixture.py` 已有受控异步缺陷与修复验证。可复用其场景和断言；脚本自己注入/修复缺陷的结果，只证明机械测试链，不能冒充真实 Agent 浏览器诊断能力。[R9]

**证据：** 记录宿主/模型/工具配置版本、实际动作、独立预期、首次失败、修后结果与必要回归。原生工具没有提供的日志或网络观测要明确缺失，不能伪造回执。

**正式受管验收：** 原生 Browser Use 不能被现有 proof consumer 直接消费时，探索结果不替代最终证明；继续使用项目真实可运行的检查或显式报告缺口，不新建一个未经验证的“把聊天转通过”适配器。

## 5. 最小验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| Spec 只要求方案 | 提交方案，不启动产品实现 |
| 普通 TDD -p | 原生独立任务可并行，不自动启动外部 CLI runner |
| 宿主支持后台 | 主回合进度回复后任务可按该宿主语义继续；工程波保持未收口 |
| 宿主能力未知 | 不假定后台存在、不释放归属、不误报完成 |
| 中途聊天反馈 | 只协调相关 worker；发送不冒充消费；契约改变需按已有规则绑定 |
| 浏览器工具不在子 Agent 中 | 调整到实际可执行者或报告缺口，不虚构工具调用 |
| 独占页面/设备 | 只有一个操作者；无关纯代码工作仍可推进 |
| 查看进度 | 未收口不等于 zombie/运行中；只读，不隐式测试或删除 |
| 固定版本 A 与增量 B | A 产物不变，B 可独立推进，旧批准不接受新产物 |
| 最终汇总 | 已完成、已验证、未完成及 CI 状态分开；没有必需证据就不报全绿 |

通过某个夹具不代表所有宿主/平台通过。文档规则测试、确定性集成检查、真实模型/宿主验收分别报告。

## 6. 如何安全退役，而不是鲁莽删代码

先从默认路径移除不必要调用和规则加载，保留显式旧入口。确认实际引用、安装器、测试、活动批次和历史证明的消费者后，再决定是否删除独立模块。

本轮不迁移 active batch 的 schema，不清除 frozen runtime，不删除回执和旧版本，不以文件年龄推断无用。不再使用一个展示缓存可以重建；丢失一次真实失败证据则不一定能恢复，两者分开处理。

不依据单纯文件大小拆模块，不为了“只有两个 PR”压缩不同授权风险的修改。注释硬门的降级如果被确认，单独提交。

## 7. 效果口径

先保证代表性场景的原验收义务不退化，再比较人工需要追加的“继续”次数、重复确认/搬运材料次数、重复检查次数，以及从收到反馈到实际复验的耗时。

复用现有回执和显式 /eval；不建设独立遥测服务。真实 provider usage 不可得就填未知。模型评测、安装浏览器或产生外部副作用，必须在相应的明确授权与预算内执行。零错误指本轮测试中的观察，不是对任意未来运行的绝对保证。
