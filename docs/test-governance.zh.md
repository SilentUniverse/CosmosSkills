# 测试质量、触发范围与运行成本

项目推进后，测试数量本身不能说明质量，单次全量通过也不能说明成本受控。
这套治理进入现有 Spec、TDD、TIDY：开发者继续表达目标、审核实际版本和反馈效果，
AI 负责选择检查、保留证据、维护测试与解释成本变化。

## 日常怎么用

| 开发阶段 | 开发者表达 | AI 执行 |
|---|---|---|
| Spec | “实现导入，取消不能留下半份数据” | 建立行为与验证器映射；约定相关模块、集成、交付及长时检查的触发点 |
| 局部实施 | “继续做完这些 Issue” | 修改后跑直接相关用例；卡完成时覆盖模块和消费者；审查新增测试的检测能力 |
| 人工审查点 | “导入能完整试用时给我一个版本” | 聚合所需 Issue，跑场景和实际产物检查；版本实测后才通知 |
| 最终交付 | “把反馈修完并交付” | 在最终候选完成全部适用交付门；相关修改使旧证据失效 |
| 测试变慢 | “查一下测试为何变慢” | 先读回执，再按需启用原生逐例计时；定位重复验证、慢项与环境差异 |
| TIDY | “清理这个目标” | 清理已释放临时文件；保留测试、可复用场景、回执和交付历史 |

不需要为每个测试维护一张卡，也不需要多调用一个 Flow。小项目继续使用原生测试命令和
`CODEBASE.md` 的验证入口；只有确有选择需求时才维护少量验证组。每个组说明用途、责任方、
影响路径。共享 fixture、依赖、配置和跨模块消费者也属于影响范围。未知路径或空变更集选全量，
重命名核对新旧路径，明确要求全量时直接绕过筛选。

人工仍审核产品行为、体验、需求选择和固定交付版本。新增测试由 AI 在既有代码审查中检查；
如需改变已接受的质量义务、移除必需检查或接受覆盖缺口，才呈现具体风险供你决定。
普通慢测试定位、去重和保持同等检测能力的重构沿用已有实施授权。

## 什么测试值得留下

[质量标准](../workflow/tdd/tests.md)要求可说明：哪种真实错误会使测试失败，预期值为何独立于
实现，是否依赖顺序、时钟、共享数据或泄漏资源，是否有独特覆盖，以及失败能否定位。
优先使用能证明该行为的最小稳定接口；需要真实 IO、事务或跨进程行为时保留相应集成检查。
单断言、覆盖率数字、文件数和“从未失败”都不能代替这项判断。

首次失败始终保留。诊断性重试不把失败改成成功；隔离不稳定测试需要责任方、修复 Issue、
原因、复查期限和受影响义务。必需覆盖没有实际运行的替代检查，就仍未完成。当前提供的是
工作流约定与证据，不会自动创建隔离平台或替人批准覆盖例外。

测试删除要求行为已退役或更便宜的检查保留相同错误检测能力。TIDY 可以指出待调查项，
不能自动删除测试源码，不能把回归场景当成临时文件清掉。

## 共享运行与复用

主控汇总共享检查，子 Agent 只做各自局部诊断。受管批次中，同一固定候选、检查、输入与环境下的活动请求
返回同一 run ID；重入不增加运行预算，执行器锁确保命令体只执行一次。不同检查在前一项终态前
拒绝准入；调用方观察现有运行后再提交。运行共享使用现有主控和受管状态，不依赖常驻模型轮询或另一套待执行队列。普通 supervisor 调用不自动去重，
由主控协调共享检查。状态读取与受管验证器的状态写入会对短暂锁冲突做有限等待，
避免一次状态查看让后台验证器退出；等待不追加执行次数或接管别人的锁。

完成结果复用默认关闭。受管批次的隔离检查可显式声明 `reuse: true` 和完整
`reuse_environment`，运行器读取实际工具及声明依赖树的字节形成身份，再绑定检查名、候选、
命令、验证 epoch、产物输入、需求、上游证明和决定。只读 lockfile 不能证明安装环境没变。
缺失环境、无法解析工具或不满足隔离条件时重新执行；失败不进入缓存。

调用方必须能说明依赖闭包和可变外部状态；这不是自动发现完整依赖的工具。UI、资源、应用
生命周期不能启用该缓存。大依赖树哈希也有成本，应先估算它是否比重跑便宜。
不启用复用时不扫描依赖树，非 UI 任务不读取 UI 专属规则或启动、安装浏览器。

## 时间和预算是三件事

| 约束 | 回答的问题 | 判定 |
|---|---|---|
| 固定性能基线 | 同等条件下是不是更慢了 | 固定命令、硬件/依赖/缓存/并发口径，比较足量样本 p50 或 p95 |
| 单命令硬超时 | 命令是否失去边界 | 到时停止所属进程树，保留失败和终态证据 |
| 原目标累计预算 | 是否因重试、重开而不断追加成本 | 累计准入次数和命令/生命周期预留时间，不能靠重开清零 |

现有回执 `duration_class` 的 normal/slow/near-timeout 只表示离超时多远。
`performance` 没有固定基线时为 `unmeasured`。调大 timeout 不会改变性能比较。
整项作业的复制、准备、场景、回收、排队也要看；命令预算不等于覆盖所有这些阶段的全局硬截止。
多个作业耗时相加不是 CPU 时间，也不是并行工作流的关键路径。

## 怎么量化优化效果

先保存实际旧版本，包含未提交代码；先固定比较口径与允许波动，再运行新版本。
普通开发无需为了生成报表反复全量运行。需要测评时使用同一机器，固定依赖和缓存条件，
隔离其他构建任务，交错运行旧、新版本。样本数与容差依据项目实测设定。

1. **功能与质量。** 相同需求、最终验收、平台和缺陷反例必须通过。统计选择检查是否漏掉了独立
   完整检查发现的失败；漏检未解释前扩大范围。快但丢掉义务的运行不算收益。
2. **运行次数与成本。** 收集全量次数、相同候选重复次数、失败次数、作业总耗时、队列时间，
   对照并发和机器条件。先读命令回执，需要定位时再开原生逐例计时。
3. **固定基线。** 显式 `measurement_context` 标识机器/运行时/依赖/冷热缓存/并发；相同字符串
   是调用方声明，工具不会检测所有环境漂移。没有这个口径不能生成可比基线。
4. **判断回退。** 比较同一组足量成功样本。失败、缺时间、样本不足、环境不同不能判为性能通过。
   单个超线样本只提示调查，不能直接断言稳定回退；不得刷新基线把回退吞掉。
5. **完整工作流。** 若要比较 AI 产物质量、任务总时间和 token，显式开展配对模型评估，记录全部
   Agent 与失败调用的真实 usage、人工等待和返工；CLI 耗时或文本 token 数不能替代模型吞吐。

仓库内可直接运行以下命令，其他项目沿用自己的原生测试器：

```sh
python scripts/run-tests.py --durations-file .scratch/tmp/run-01-durations.json
python workflow/test-governance.py report --root . --receipts RECEIPT_01.json RECEIPT_02.json --output REPORT.json
python workflow/test-governance.py report --root . --batch BATCH_ID
python workflow/test-governance.py baseline --report REPORT.json --group GROUP_KEY --statistic p50 --min-samples 5 --relative-tolerance 0.10 --absolute-tolerance-seconds 1 --output BASELINE.json
python workflow/test-governance.py compare --report CANDIDATE_REPORT.json --baseline BASELINE.json
```

这里的 5 次、10% 和 1 秒只是命令示例，使用时替换为预先确定的口径。`GROUP_KEY` 来自 report。
同一个回执的副本不重复计数；真实重跑和失败各自保留。输出文件拒绝覆盖，默认 stdout 只显示
成本最高的 10 组，完整观察放在指定报告。比较退出码：0 在目标内、1 观察到回退、2 无法判定或
输入无效。supervisor 的单次性能观察不改变功能退出码；性能 AC 使用独立比较命令作门。

## 本仓库 CI

[验证组策略](../tests/test-policy.json)控制已有检查：文档变更跑目录校验；行为运行时变更跑
Linux/macOS/Windows 回归；影响 UI 或打包的路径加上相应真实夹具；公共执行底座同时触发相关
消费者。策略/CI 自身变更和未知路径跑完整矩阵。手动 `workflow_dispatch` 也跑完整矩阵。
CI 按适用范围触发检查；最终交付遵守全部适用必需检查。

回归作业保存完整回执、日志和逐例耗时。矩阵内同时运行最多 2 项，各作业设硬超时。并发上限控制同时占用的 runner 数，可能延长完整
矩阵耗时；不能把降低并发直接算成节省总 runner 时间。每个分支的
运行使用 concurrency；运行中作业继续完成，后来的提交替换尚未开始的旧等待运行，遵循
[GitHub 的并发语义](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。
`required` 汇总门核对所有被选中作业实际成功；选中作业被跳过也不能绿。分支保护应使用这个
汇总检查，仓库外的分支保护设置没有由本地修改自动配置。

验证记录见[测试治理验证](benchmarks/test-governance-validation.json)，文本与 CLI 成本见
[成本比较](benchmarks/test-governance-cost.md)。本机结果不代替 Linux/Windows 原生 CI，
确定性检查通过也不能证明端到端模型质量、token 或速度已经改善。
